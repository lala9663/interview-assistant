# interview-assistant

사내 채용 면접을 돕는 AI 면접 어시스턴트 PoC다. JD로 서류를 선별하고, 면접 중 전사와 꼬리질문 후보를 띄우고, AI 참고 점수와 면접관 기록을 나란히 남기고, 면접관 일정을 맞춘다.

- 합격·불합격은 언제나 사람이 정한다. AI 점수는 참고용이고 면접관 점수와 합산하지 않는다.
- LLM에는 비식별 텍스트만 간다. 이름·연락처는 원본 영역에 암호화해 두고, 호출 직전에 가드가 한 번 더 본다.
- 음성은 서버 밖으로 나가지 않는다(로컬 STT). 서류 속 그림은 OCR로 글자만 꺼내고 모델로 보내지 않는다.
- 모든 AI 모델은 provider로 갈아 끼운다. 어떤 모델을 쓸지는 관리자 화면에서 정한다.

실행 위치(사내 서버, 사내 클라우드, 에이전트 플랫폼 안)는 아직 정하지 않았다. GCP에서 돌리지 않는다. 사내 에이전트 플랫폼에는 MCP 서버로 붙는다.

## 9개 요구사항과 상태

2026-10-30 main 기준. 지금은 AI가 fake provider로 돌아 흐름만 확인했고, 실제 LLM을 붙인 품질 검증이 남았다.

| 번호 | 요구사항 | 상태 | 화면 |
| --- | --- | --- | --- |
| FR-01 | JD 기반 서류 선별, 프로필 저장 | 구현됨. 업로드와 채용 사이트 연동(가짜 사이트로 검증), PDF·DOCX·PPTX·HTML·HWP·HWPX·구형 .doc/.ppt·JPG/PNG, 쪽마다 텍스트 또는 OCR | 서류 선별 |
| FR-02 | 직군별 역량 사전 | 구현됨. 차수별 역량과 1~5점 행동 기준(BARS) AI 초안 → 사람이 확정 | 공고·역량 사전 |
| FR-03 | 선별한 서류 기억 | 구현됨. 프로필·적합도·근거를 DB에, 서류 → 각 차수 → 최종 진행 | 서류 선별 |
| FR-04 | 면접 중 지원자 특징 기억 | 구현됨. 지원자 카드, 메모, 2차부터 이전 차수 요약 | 실시간 면접 |
| FR-05 | 실시간 면접, 대면·비대면 | 대면 구현됨(브라우저 마이크, 한 마이크면 질문 중/답변 듣는 중 전환). 비대면(WebRTC)은 계획 | 실시간 면접 |
| FR-06 | 질문, 꼬리질문, Q&A 저장, STT | 구현됨. 사전 질문, 질문 은행 후보 먼저 + AI 후보 스트리밍, 로컬 Whisper 전사, 면접 뒤 재전사 | 실시간 면접, 질문 은행 |
| FR-07 | 객관적인 답변 평점 | 구현됨. AI 참고 점수(근거 인용 필수, 3회 중앙값, 평점 기준 예시). 면접관 점수와의 일치도 검증은 실제 LLM 뒤 | 평가 |
| FR-08 | 면접관 기록 | 구현됨. 면접관 점수·코멘트, 메모, 차수 결정과 이력, 다음 차수에서 확인할 점 | 평가 |
| FR-09 | 면접관 일정, 빈 시간 맞추기 | 구현됨. 가용 시간 입력, 공통 빈 시간, 면접 잡기. 사내 캘린더 연동은 계획 | 면접관 스케줄 |

남은 큰 일: 실제 LLM 연결(사내 모델 서버), 로그인(SSO), 비대면 WebRTC, 채용 사이트 실제 연결, 실행 위치 결정. 단계별 체크리스트는 [docs/implementation-order.md](docs/implementation-order.md).

## 빠른 시작

필요한 것: Python 3.12와 [uv](https://docs.astral.sh/uv/), Node 24 이상. 자세한 설치와 환경변수는 [docs/setup.md](docs/setup.md).

```bash
uv sync --extra whisper --extra ocr --extra embedding --extra agent --extra denoise
cp .env.example .env
```

`.env`에 `IA_ENCRYPTION_KEY`를 채운다(만드는 법은 setup.md). 사내 모델 서버가 아직 없으면 첫 기동 전에 `IA_PROVIDERS_FILE=config/providers.fake.yaml`로 바꾼다. 그러면 모든 AI가 fake로 돈다.

```bash
uv run alembic upgrade head
uv run python scripts/seed_demo.py --reset
uv run uvicorn interview_assistant.main:app --reload       # http://localhost:8000
```

```bash
cd frontend
npm ci
npm run dev:api        # 백엔드에 연결 → http://localhost:5173
npm run dev            # 또는 백엔드 없이 모의 API로
```

로그인(SSO)이 붙기 전까지는 시드의 김서연(E24017, 관리자)이 로그인한 면접관이다. 테스트는 `uv run pytest`와 `frontend/`에서 `npm run check`.

## 모델은 어디서 정하나

화면 **관리자 > 모델 설정**(`/admin/models`)에서 역할마다 provider를 고르고, 연결 테스트를 한 뒤 재시작 없이 적용한다. 이력에서 되돌릴 수 있다. `config/providers.yaml`은 새 DB가 처음 기동할 때의 기본값일 뿐이다. 사용법은 [docs/ai-models.md](docs/ai-models.md).

| 역할 | 지금 기본값 | 비고 |
| --- | --- | --- |
| LLM | `open_model_server`: 사내 오픈 웨이트 모델 서버(vLLM·Ollama 등)에 OpenAI 형식 API로 | 사내 모델은 Gemma 4로 예상(확인 필요). OpenAI 서비스는 쓰지 않는다. Claude API(`anthropic_api`)는 외부 개발 테스트용으로만 |
| STT | 로컬 faster-whisper: 실시간 small, 사후 large-v3 + 면접 뒤 녹음 재전사 | GPU가 없어서 실시간은 작게, 기록은 크게 |
| 임베딩 | 로컬 BGE-M3 int8 | 질문 은행 검색과 같은 질문 거르기 |
| 답변 끝 판정 | Smart Turn v3 (1초, 0.8) | 모델 파일이 없으면 침묵 2초 |
| 화자분리 | fake | 면접 흐름에서 쓰지 않는다. 화자는 마이크의 역할 기록으로 붙인다 |
| 서류 읽기 | PaddleOCR(PP-OCRv5 한국어), syhwp, LibreOffice | |

## 3. 중요한 것 (일하는 원칙)

- **범위 통제**: 요구사항 안에서 깊게 판다. 현업이 넓게 말해도 우리가 잘라낸다.
- **깊이**: 현업이 생각하지 못한 부분을 AI로 어떻게 풀지 보여준다. AI가 그려준 그림을 그대로 붙이지 않는다.
- **현실성**: 면접관, 경력 지원자, 신입 지원자 입장에 대입해 실제로 쓸 수 있는지 확인한다. 엉뚱한 아이디어도 적어 두고 나중에 버린다.
- **속도**: 매일 아웃풋을 낸다. 현업도 주 단위로 보고하므로 미팅마다 목업 수준의 진척을 보여준다.
- **질의는 메일로**: 회의가 끝나면 회의록과 질문을 바로 메일로 보낸다. 다음 미팅까지 기다리지 않는다.
- **주도성**: 모르는 것은 자료를 요청한다. 채용 담당자 인터뷰도 요청한다. 연락 창구가 피플팀으로 정해져 있으면 그 경로를 따른다.
- **근거**: 합의한 범위와 요구사항은 문서로 남기고 컨펌을 받는다.

## 4. 기술·환경에서 나온 것

- **목업**: 뒤(이관)를 생각하지 말고 Python 기반으로 빠르게 만든다. 로컬 에이전트 방식으로 목업하고 피드백을 반복한 뒤 공통 코어를 유지한 채 포털로 옮기는 방식이 제안됐다.
- **피플팀 표준**: 쿠버네티스 기반 PaaS가 레포를 만들어 주고 Jenkins로 배포한다. 표준 스택은 Java 8 / Spring Boot 2.7이고, 17·21로 올리려면 근거가 필요하다.
- **현업 선호**: 프론트(Vue 3)와 백엔드는 Java 웹 형태, 에이전트는 Python + LangChain/LangGraph.
- **자원**: API 구독과 RAG 필요 사유를 담당자와 협의 중이다. 데이터가 민감해 사내 RAG나 시크릿 LLM 사용을 논의하고 있다.

- 사전(Pre) / 면접 당일 / 사후(Post) 단계로 나누고 단계마다 "과제"인지 "시스템"인지 표시
- 현업이 요청한 범위만 포함하고, 참고 솔루션에만 있던 기능(포지션 추천 등)은 제외
- 사전 처리(데이터 매핑, 면접관 매칭 등)가 필수라면 리스크로 명시하고 1단계/2단계로 구분

### 2. 면접 환경 및 리스크 정의

- 면접 형태: 1:1인지 다대다인지, 대면인지 화상인지
- 화상면접 음성 수집 방식: 녹스 미팅에서 API로 받을 수 있는지, 안 되면 브라우저 오디오 탭 공유가 가능한지
- 환경 리스크: 노이즈, 마이크 한계 등

### 3. 세부 업무 플로우 (가장 핵심)

- 행위 기반으로 단계를 나누고, 단계별로 연관 시스템·AI, 필요한 기술 요소, 예외 케이스 처리 기준을 정리
- AI 부분은 구체적으로 작성
  - 추천 질문과 꼬리 질문을 어떤 프롬프트·스킬로 만드는지
  - 추천 방식에 대한 가이드
  - 근거로 쓰는 팩트 데이터(이력서, JD 등)
- 저장 방식(세션 일괄 저장인지 실시간인지, 어떤 이벤트에 저장되는지) 같은 디테일까지 포함

### 4. 시스템 구성도

- MCP 서버 사용 여부
- RAG용 벡터DB(Qdrant 또는 ES)
- LLM 종류(사내 시크릿 LLM 가능 여부)

### 5. 자원 신청 근거

- 무엇이, 왜, 얼마나 필요한지
- 데이터 민감성을 고려해 사내 RAG·LLM 사용 여부를 반영

### 6. 개발 환경 정리

- PaaS 배포 방식(자동 배포인지 Jenkins 수동 실행인지)을 정확히 파악
- 기술 스택: Vue3 + Java 백엔드, Python + LangChain/LangGraph 에이전트
- 목업은 우선 Python으로 빠르게 제작

### 7. 요구사항 정의서 및 컨펌 메일

- 업무환경 정의서와 과제 요구사항 정의서 샘플을 기반으로 작성
- 메일로 현업 컨펌을 받아 근거로 확보

## 중요한 것 (원칙·태도)

- **범위 통제**: 요구사항 안에서 깊게 파고들고, 요청 없는 기능을 같은 레벨로 넣지 않기
- **깊이**: 박스와 흐름도 수준이 아니라 현업보다 더 깊이 고민한 흔적 보여주기. 현업이 생각하지 못한 부분을 AI로 어떻게 풀지 제시
- **현실성**: 면접관과 지원자(경력/신입) 입장에 직접 대입해 실제로 쓸 수 있는 서비스인지 검증
- **속도와 애자일**: 매일 아웃풋을 내고, 미팅마다 목업 수준의 진척을 보여주기
- **미팅 시간 활용**: 질의는 회의 직후 메일로 보내고, 미팅은 결과물 중심으로 진행
- **주도성**: 끌려가지 말고 선제적으로 질문하고 자료를 요청. 채용 담당자 인터뷰도 직접 요청
- **근거 확보**: 합의한 내용은 반드시 문서화하고 컨펌을 받기

# 회의록: AI 면접 지원 시스템 요건 협의

> ※ 녹취 STT 품질이 낮아 일부 내용은 문맥으로 추정함. 발화자 1·2는 개발사, 발화자 3·4는 현업으로 보고 정리함.

## 1. 개요
- **목적:** 지난 미팅 내용을 바탕으로 과제 범위를 확인하고, 필요한 데이터와 리스크를 점검함
- **범위:** 면접 도메인 개발을 면접 전(사전 DB), 면접 중, 면접 후(리포트) 세 단계로 구성함

## 2. 면접 전: 사전 DB 구축

### 신입 지원자 데이터
- 채용 사이트를 그룹이 관리하고 있어 API 제공은 불가함.
- 대신 공채마다 동일한 엑셀 포맷이 나오고, 변수명도 바뀌지 않음.
- 전체 지원자가 아니라 서류와 GSAT를 통과한 면접 대상자만 엑셀로 업로드하는 방식임.
- 엑셀에는 자소서, 학력, 과목별 정보 등 6~7개 유형이 들어 있으며, 어떤 항목을 활용할지는 현업이 추후 결정함.
- 파일에 DRM이 걸려 있어 해제 신청이 필요함. 신청은 서버 도메인과 IP 기준으로 진행함.

### 직무 / JD
- 신입 직무 유형은 10여 개로 고정되어 있음.
- JD는 공고 등록 에이전트에서 생성되며, 연결 가능성이 있음. 다만 신입은 JD까지 반영하지 않아도 될 것으로 봄.

### 경력 데이터
- 글로벌 채용 포털에서 API로 제공될 가능성이 있으며, 현업이 담당자에게 확인할 예정임.

### 면접관-지원자 매핑
- 별도 시스템 없이 엑셀로 관리함. 현업 담당자가 만든 에이전트가 엑셀로 산출함.
- 결론적으로 현재 모든 데이터는 엑셀 기준임.

### 화면
- 엑셀 업로드 화면이 필요하며, 개발사가 목업으로 준비함.

## 3. 면접 중

### 기본 흐름
- 1차 리포트(요약과 추천 질문)를 확인한 뒤 면접을 진행함.
- 면접 중에는 답변에 따라 꼬리 질문을 생성하고 피드백을 기록함.

### 면접 유형
- 신입은 PT(직무) 면접과 인성 면접이 있음.
  - 직무 문제 출제는 별도로 이루어지며, 범위에 포함되지 않음.
  - 질문 생성은 전공 과목과 자소서 프로젝트 기반으로 함.
  - PT 면접은 세션 구분이 명확해 오히려 AI 성능이 좋을 것으로 예상함.
- 경력은 포트폴리오, 직무, 인성 등 여러 차례 면접을 봄.
- 따라서 1인당 여러 면접을 등록할 수 있는 구조로, 면접 유형별로 케이스를 분리해 설계함.

### 질문 가이드
- 현업에 정리된 기준은 없음. 현업이 1차본을 작성해 제공하고, 연구 결과는 추후 보완함.
- 개발사는 JD별 실제 질문 샘플을 많이 받을수록 정확도 검증(evaluation)에 유리하다고 설명함.

### 화상 면접 (Knox 미팅)
- 음성이나 텍스트를 API로 받을 수 있는지, 실시간 자막 기능이 있는지 확인이 필요함.
- 실시간 연동이 불가하면 면접 후 요약 리포트 수준으로 기능이 축소될 수 있음.

### 실시간 추천 질문 이슈 (개발사 시뮬레이션 결과)
- STT, LLM, JD 매칭을 거치면서 3~10초 지연이 발생하고, 추천 질문이 계속 바뀌어 면접관이 혼란스러울 수 있음.
- 대응: 사전 생성 질문 위주로 진행하고 추가 질문은 자유롭게 하도록 면접관 가이드를 제공하는 방향으로 현업과 합의함.
- 신입 면접은 주고받는 템포가 느려 문제가 덜하고, 경력 면접에서는 이슈가 생길 수 있음. 이 점을 UX 설계에 반영함.

### 금지 질문 / 블라인드
- 성별이나 가족 관련 정보 등은 질문과 요약에서 제외해야 하므로 기준이 필요함.

## 4. 면접 후: 리포트

### 성격
- 참고용이며, 공식 평가는 사람이 함.
- 향후 AI 평가(면접관 편차 보정)로 확장할 가능성에 대비해 평가 항목 구조를 미리 고려함.

### 메일 발송
- Knox 메일로 발송 자체는 가능함.
- 발송 시점과 사람의 컨펌 절차를 정의해야 함. 기능을 먼저 개발한 뒤 연동을 검토함.

### 리포트 생성 시점
- 신입은 면접 직후 1~2분 안에 등급을 입력함. 경력은 30분~1시간 뒤에 입력함.
- 개발사 제안: 실시간 STT로 초안을 빠르게 제공하고, 전체 음성을 다시 STT 처리한 보정본은 이후 제공하는 방식(자동 또는 수동 버튼)

### 면접관 입력 시스템
- 그룹 신입채용시스템에 입력하며, 연동은 어려움.
- 동일한 화면 구성으로 만들어 복사·붙여넣기가 가능하도록 함.
- 우리 화면에서 입력한 내용이 저장된 것으로 착각하지 않도록 UX 주의가 필요함.

### 분량
- 신입은 간단한 코멘트, 경력은 상세하게 작성함.

## 5. 개발 환경 및 리스크

### 현황
- 인프라를 로컬에서 동작 확인했고, API 신청과 테스트를 완료함. Whisper 음성 인식은 테스트 중임.

### DB
- 개발용 DB만 받은 상태이며, 운영 DB에는 실제 개인정보가 있음.
- 당분간 기존 DB를 사용하고, 테이블은 개발사가 자체 생성함.
- 개인정보 처리와 KMS 적용이 필요함.

### 동시성 리스크
- 신입 공채 기간(상·하반기 약 1주)에 약 20개 면접이 동시에 진행되면 API 성능 문제가 생길 수 있어 확인이 필요함.

### 화자 분리 리스크
- 현재 Whisper(오픈웨이트)는 화자 분리를 지원하지 않음.
  - LLM 문맥 기반 분리는 면접관과 지원자 구분 정도만 가능하고, 면접관 여러 명은 구분하지 못함.
  - 상용 버전의 지원 여부는 개발사가 확인함.
  - 마이크 분리(지원자용과 면접관용)가 가능한지 현업 확인이 필요함.
- STT 방식: 면접 중에는 실시간 STT, 최종 리포트에는 전체 일괄 재처리를 적용함.

### 녹음 파일 / 동의
- 녹음 파일은 저장하지 않음. 법적 이슈와 저장 용량 때문임.
- 지원자 동의는 사전에 받은 것으로 가정함.

### 개발 방식 제안 (개발사)
- 로컬 하네스(DB 설치 불필요)로 빠르게 vibe 코딩해 UX를 검증함.
- 이후 에이전트와 코어를 공유하는 구조로 운영 환경에 이관함.

## 6. 일정
- **계약:** 4월까지이며, 그 전에 1차 오픈이 필요함. 단계(Phase)는 별도로 정의함.
- **현업 희망 일정:**
  - 2~3월: 경력 면접으로 테스트
  - 5월: 상반기 신입 면접에 적용
  - 상반기 결과를 바탕으로 하반기 확대
- **개발사:** 플로우 기반 목업을 최대한 빨리 공유함(다음 주 수요일 일정 언급). 질문 사항은 Confluence에 올려 공유함.
