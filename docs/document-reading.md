# 서류 읽기 (텍스트 층과 OCR)

지원 서류를 원본 영역에서 텍스트로 바꾸는 단계다. 쪽마다 텍스트 층을 쓸지 OCR로 읽을지 고르고, 결과는 비식별화([deidentification.md](deidentification.md))를 거쳐야 LLM으로 간다. 그림과 원본 파일을 모델로 보내는 경로는 없다. 멀티모달 LLM에 이력서 그림을 넣으면 비식별화를 건너뛰므로 만들지 않는다.

도구와 방식은 관리자 > 모델 설정의 "서류 읽기" 묶음에서 고른다([ai-models.md](ai-models.md)). 측정은 [ocr-benchmark.md](ocr-benchmark.md).

## 쪽마다 읽는 방법

`documents/reading.py`의 `PageReader.plan`이 쪽(슬라이드, 그림 파일)마다 정한다.

| 읽기 방식 | 텍스트 층이 쓸 만함 | 텍스트 층이 없음(스캔) | 텍스트 층이 깨짐 |
| --- | --- | --- | --- |
| 자동(기본) | 텍스트 층 | OCR | OCR로 다시 읽음 |
| 항상 OCR | OCR | OCR | OCR |
| 텍스트만 | 텍스트 층 | 보류 | 보류 |

- 텍스트 층이 없다: PDF 쪽에 읽을 수 있는 글자가 30자 미만이고, 그림이 쪽의 50% 이상을 덮거나 유니코드 매핑 없는 글자가 있다.
- 그림으로 바꿀 수 없는 쪽(HWP·DOCX처럼 쪽 개념이 없는 문서)이 OCR이 필요하면 보류한다.
- 보류된 쪽이 있으면 문서 전체가 처리되지 않는다: 업로드는 422, 사이트 첨부는 `ocr_required`(텍스트만 설정) 또는 `ocr_unavailable`(OCR 엔진 없음·실패). 원문은 원본 영역에 남아 관리자가 고친 뒤 연동 현황에서 다시 처리한다.
- OCR 신뢰도가 경고 기준(기본 0.8)보다 낮은 쪽은 경고로 남긴다. 처리는 막지 않는다.
- 문서 속 그림: "문서 속 그림 OCR"이 켜져 있고 텍스트만 방식이 아니면 그림마다 증명사진인지 먼저 보고, 아니면 OCR한다. 160×160px보다 작은 그림(아이콘·로고)은 건너뛴다.

### 깨짐 판정 (`documents/quality.py`)

글꼴이 글자를 엉뚱한 코드로 매핑한 PDF는 화면에는 한글로 보이지만 "ÀÌ·Â¼­ ±ÇÇÏ¸°"처럼 읽힌다(EUC-KR 바이트를 Latin-1로 읽은 것). 비식별화가 이름을 못 찾지만 바이트를 되돌리면 이름이 나오므로 LLM으로 가면 안 된다. 그런 쪽은 숨은 텍스트까지 버리고 OCR로 다시 읽는다.

수상한 글자(공백 제외 글자 수 기준):

- 매핑 없는 글리프 `(cid:123)`, U+FFFD, 제어 문자, 사용자 정의 영역, 미할당 코드
- Latin-1 보충·확장 글자(U+0080–U+024F). 이력서에 실제로 쓰는 기호(· × ° ± © ® ² ³ …)는 두 개 이상 붙어 있을 때만
- 한글 자모 조합형·반각 한글(정규화된 텍스트에는 없다)
- 한국어 이력서에 안 쓰는 문자(키릴, 아랍, 히브리, 타이 …). 영문, 그리스 문자, 한자, 가나, 호환 자모(ㅇ 글머리)는 정상

| 민감도 | 수상한 글자 비율 | 연속 길이 | 쓸 때 |
| --- | --- | --- | --- |
| 낮음 | 30% 이상 | 보지 않음 | 외국어 이름·기호가 많은 서류 |
| 보통(기본) | 15% 이상 | 3자 이상 | |
| 높음 | 5% 이상 | 2자 이상 | 이름 하나만 장식 글꼴로 깨진 경우까지 |

비율 규칙은 20자 이상일 때만 본다. "José"의 é는 길이 1이라 통과한다. 테스트: `tests/test_document_quality.py`.

### 증명사진 판정 (`documents/images.py`)

OCR도 얼굴 인식도 없이 그림의 모양과 색 분포로 본다. 증명사진은 읽지 않고 버리고, 이유는 리포트에 남는다.

- 세로형: 가로/세로 0.62–0.92 (3:4는 0.75)
- 작음: 쪽·슬라이드 면적의 10% 이하. 위치를 모르는 그림 파일은 160만 화소 이하
- 글자 그림이 아님: 320px 회색 사본에서 가장 많은 색 ±24 = 바탕, 80보다 먼 색 = 글자, 나머지 = 중간. 바탕 70% 이상·글자 0.3% 이상·중간 20% 이하면 글자 그림(자격증, 캡처, 스캔)이다. 사진은 단색 배경이어도 얼굴·머리·옷 때문에 중간 색이 많다.

세 조건을 모두 만족하면 증명사진이다. 판정은 문서 안에 붙은 그림에만 한다. 그림 파일(JPG·PNG) 자체는 이력서를 찍거나 캡처한 것으로 보고 통째로 OCR한다. 카카오톡으로 줄어든 세로 사진은 크기·비율이 증명사진과 같아 잘못 버릴 위험이 크기 때문이다. 증명사진 파일만 올리면 OCR 결과가 거의 비어 선별할 내용이 없다. 사진은 받지 않는 항목이다([site-intake-spec.md](site-intake-spec.md) 6장).

### 기록

지원서마다 `Application.document_info.reading`에 남는다(설정 revision, 읽기 방식, 그림 OCR 여부, 민감도, 도구와 버전, 파일마다 OCR한 쪽·최저 신뢰도·읽은 그림·버린 증명사진·깨진 쪽). 서류 선별 상세 패널의 "서류 읽기" 줄이 이것을 보여 준다. 처리 중에 설정을 바꿔도 그 지원서는 시작할 때의 설정으로 끝난다(`runtime.models.active`를 한 번 잡아 AI와 읽기 도구를 같은 스냅샷에서 꺼낸다).

검토 리포트(`check_leaks.py --documents --report`)는 쪽마다 방법·이유·도구·신뢰도·시간, 그림마다 판단과 이유를 표로 보여 준다.

## OCR 엔진

| 엔진 | 위치 | 라이선스 | 상태 |
| --- | --- | --- | --- |
| PaddleOCR 3.7 + PP-OCRv5 (mobile 검출 + 한국어 인식) | 이 PC, CPU | Apache-2.0 | 권장. 모델 32MB(server 116MB) |
| Tesseract 5.4 + kor+eng (tessdata best·fast) | 이 PC | Apache-2.0 | 비교용. 빠르고 가볍지만 한국어 오류가 많다 |
| Google Document AI | 사내 GCP | 상용 | 카탈로그만, 구현 전·자격증명 없음 |
| Naver CLOVA OCR | 외부 | 상용 | 카탈로그만, 구현 전·자격증명 없음. 서류 그림이 회사 밖으로 나간다 |

모델 파일은 관리자가 화면에서 "다운로드"를 누를 때만 받는다(크기 표시, 커밋·파일 고정, sha256 검증, 이어받기). `weights/`는 git에서 빠져 있다. OCR 결과에는 엔진 이름·버전·신뢰도가 남는다.

PaddleOCR 옵션: 모델(mobile·server), 줄 방향 보정(끔, 똑바른 스캔의 줄을 뒤집어 망가뜨린 적이 있다), 쪽 방향 보정(끔, 옆으로 찍은 휴대폰 사진이 많으면 켠다), 그림 긴 변 제한(2400px), CPU 스레드. paddlepaddle은 3.2.2로 고정했다(3.3.1의 oneDNN이 Windows CPU에서 실패하고, oneDNN 없이 돌리면 4배 느리다).

PaddleOCR은 서버와 다른 작업 프로세스에서 돈다(`providers/isolated.py`). Paddle이 함께 싣는 Intel OpenMP(`libiomp5md.dll`, 2019년 빌드)가 CTranslate2(faster-whisper)가 쓰는 것(2025년 빌드)보다 오래되어, 한 프로세스에서 PaddleOCR이 먼저 올라가면 Whisper가 "WinError 127"로 로드되지 않았다. Windows는 이미 올라간 같은 이름의 DLL을 다시 쓰기 때문이다. 지금은 서버 프로세스가 paddle을 아예 불러오지 않고 쪽 그림을 작업 프로세스에 보내 줄 목록을 받는다. 작업 프로세스는 처음 쓸 때(적용할 때의 워밍업) 뜨고, 죽거나 10분 안에 답하지 않으면 다음 요청에서 다시 뜨며, provider가 내려가거나 서버가 끝나면 같이 끝난다. 두 엔진을 함께 켠 상태는 `tests/test_engines_together.py`가 확인한다.

### OCR 오독 대책

OCR은 글자를 비슷한 글자로 잘못 읽는다. 잘못 읽은 이름·전화번호는 비식별화 규칙을 비껴가므로 두 겹으로 막는다.

1. 비슷한 글자 고치기(`documents/ocrfix.py`, 모든 OCR 줄): 숫자가 대부분인 덩어리 안의 O·l·I·S·B 등은 숫자로("010-138l-O274" → "010-1381-0274"), 글자 사이의 ©·®는 @로.
2. OCR 구간에만 쓰는 너그러운 탐지기(`deid/detectors/ocr.py`):
   - 지원서에 적은 이름·학교·회사와 자모 거리 1(5자 이상은 2) 이내인 값. 단어 경계 없이 찾는다("저는설도현입니다", "광운대전자공학")
   - 띄어 쓴 두 글자 이름("하 준 님"), 호칭이 잘린 이름("석 님")
   - 전화번호 숫자 편집 거리 1, 이메일·영문 이름의 글자 뼈대
3. 누출 검수도 따로 본다(`deid/leaks.py`): 정답 값과 자모 근사 일치, 숫자 편집 거리 1까지 "근접 누출"로 센다.

## HWP 도구 결정

- 채택: HWP 5.0은 syhwp 0.0.8(MIT, 순수 파이썬, 버전 고정)로 컨테이너를 열고 압축 해제·배포용 문서 복호화·레코드 분해를 맡기고, 레코드 트리는 직접 읽는다(`documents/hwp.py`). syhwp 자체 텍스트 출력은 머리글·각주·숨은 설명을 본문에 섞고 문서 정보와 링크를 읽지 않아서, 공개된 HWP 5.0 규격의 컨트롤 id로 블록을 나눈다. 문서 요약 정보는 OLE 속성 집합을 직접 읽는다(olefile 0.47의 `getproperties`가 VT_LPWSTR을 4바이트 앞에서 읽는 버그가 있다).
- HWPX는 ZIP 안 XML(OWPML)이라 lxml로 직접 읽는다(`documents/hwpx.py`).
- hwplib(Apache-2.0, Java)은 비교 후보로 카탈로그에만 둔다. syhwp로 요구 항목(본문, 표, 머리글·바닥글, 각주, 글상자, 메타데이터, 숨은 텍스트, 암호 거부)이 다 되었고, hwplib을 쓰려면 Java 런타임(이 PC에 없음)과 JVM 연동이 더 필요하다.
- pyhwp는 AGPL이라 쓰지 않는다.
- 위험: syhwp는 1인 프로젝트(별 1개, 커밋 20개)이고 비공개 함수(`_read_hwp5`)를 쓴다. 버전을 고정했고, 깨지면 같은 인터페이스로 hwplib이나 자체 구현으로 바꾼다. 실제 한글 프로그램으로 저장한 HWP로는 아직 확인하지 못했다(아래).

## 구형 .doc·.ppt

LibreOffice headless로 .docx·.pptx로 바꾼 뒤 같은 추출기로 읽는다(`documents/legacy.py`). 변환마다 임시 폴더와 버리는 사용자 프로필을 쓰고(열려 있는 LibreOffice와 충돌 없음), 매크로는 실행되지 않으며, 120초 제한이다. LibreOffice가 없으면 "변환기 없음"(`converter_missing`)으로 거부하고 관리자 화면에 "프로그램 LibreOffice 없음"이 보인다. 설치는 [setup.md](setup.md).

## 알려진 한계

- 실제 한글 프로그램으로 저장한 HWP·HWPX 샘플이 없다. R22(HWP 5.0)는 규격대로 코드로 만든 파일이다. 한컴오피스로 가상 이력서를 HWP와 HWPX로 저장해 `tests/fixtures/resumes/`에 넣고 정답 목록에 추가해야 한다.
- HWP 5.0의 흰 글씨는 숨은 텍스트로 나누지 못한다(글자 모양이 DocInfo에 있어 아직 안 읽음). HWP 5.0 메모는 본문으로 읽는다. 둘 다 비식별화는 된다.
- 다른 한글로 잘못 매핑된 글꼴(형식은 멀쩡한 엉뚱한 한글)과 영문만 섞인 깨짐은 판정하지 못한다. 언어 모델이 필요하다.
- Tesseract는 이 서류들에서 한국어 오류가 많다(글자 오류율 최대 90%대). 누출은 없었지만 선별 품질이 떨어진다. 기본은 PaddleOCR.
- PaddleOCR server 검출은 이 노트북 CPU에서 쪽당 30초 이상이라 실사용이 어렵다.
- 휴대폰 사진은 기울기·흐림이 심하면 신뢰도가 떨어진다. 쪽 방향 보정은 기본으로 꺼져 있다.
- HEIC(아이폰 사진)·TIFF는 받지 않는다.

```bash
uv run python scripts/check_leaks.py --documents                       # OCR 없이: 스캔·그림은 보류로 분류
uv run python scripts/check_leaks.py --documents --ocr paddleocr       # PaddleOCR로 31건 전부
uv run python scripts/check_leaks.py --documents --ocr tesseract --ocr-model fast
uv run python scripts/check_leaks.py --documents --ocr paddleocr --report   # 쪽별 읽기 표가 있는 검토 리포트
uv run python scripts/bench_ocr.py --engine paddleocr                  # 쪽당 시간·메모리·글자 오류율
```

모델 파일 위치는 `IA_WEIGHTS_DIR`(기본 `weights/`) 또는 `--weights`. 결과(2026-10-26, PaddleOCR mobile): 31건 중 30건 검사, 정답 값 389개 누출 0·근접 누출 0, 암호 HWP 1건 거부. OCR 글자 오류율 평균 0.5%, 최대 2.3%. OCR 없이는 22건 누출 0, 8건 보류, 1건 거부. Tesseract best·fast도 누출 0.
