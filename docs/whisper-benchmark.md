# 로컬 Whisper 측정 (faster-whisper, CPU)

2026-10-26 · `scripts/bench_whisper.py`로 측정. 관리자 > 모델 설정의 `faster_whisper` provider가 실제로 쓰는 코드 경로(`providers/stt/faster_whisper.py`)를 그대로 돌렸다.

## 조건

| 항목 | 값 |
| --- | --- |
| PC | 노트북, Intel Core i7-1360P (4P + 8E 코어, 16 스레드), RAM 16GB, NVIDIA GPU 없음 (CPU 추론만) |
| 런타임 | faster-whisper 1.2.1, CTranslate2 4.8.2, `compute_type=int8`, CPU 스레드 12 (자동 = 코어 수 − 4). CTranslate2 기본값 4스레드보다 빠르다: medium으로 11.5초 샘플이 4스레드 12.6초, 8스레드 9.9초, 12스레드 8.9초(배터리) |
| 음성 | FLEURS 한국어 test (CC BY 4.0) 낭독 3클립: 11.5초, 22.4초, 28.9초(두 문장을 0.5초 쉬고 이음). 합계 62.7초 |
| 정답 | FLEURS 원문 전사. CER = 공백·문장부호를 뺀 글자 편집 거리 / 정답 글자 수 |
| 1회차 | 배터리 사용 중 (전원 미연결, 잔량 26% 전후) |
| 2회차 | 전원 연결, 배터리 13%에서 충전 중 |

같은 설정인데 2회차가 1회차보다 최대 2배 느렸다. 노트북 전원 관리(충전 중 전력 제한, 발열)가 속도를 크게 흔든다. 아래 속도는 범위로 읽는다. 정확도(CER)는 두 번 모두 같았다(디코딩이 결정적이다).

## 결과

"실시간 대비"는 음성 길이 / 처리 시간이다. 1보다 크면 말하는 속도보다 빨리 처리한다.

| 모델 | 파일 크기 | 메모리 (모델만 / 프로세스 최대) | 로드 | 사후 (beam 5, VAD): 실시간 대비 | 사후 CER | 실시간 스트리밍: 발화 끝 → 확정 (평균 / 최대) | 스트리밍 CER |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| small | 486MB | 0.65GB / 0.73GB | 1~2초 | 2.9~6.0배 | 13.0% | 3.5~5.7초 / 4.2~7.9초 | 13.4% |
| medium | 1.5GB | 1.7GB / 1.8GB | 5~6초 | 1.4~2.1배 | 1.2% | 7.7~8.9초 / 8.6~11.6초 | 5.4% |
| large-v3-turbo | 1.6GB | 1.8GB / 1.9GB | 5~6초 | 1.1~1.4배 | 0.4% | 11.5~18.7초 / 14.8~24.8초 | 0.8% |
| large-v3 | 3.1GB | 3.2GB / 3.3GB | 11~14초 | 0.8배 | 0.0% | 20초 / 29초 (2회차) | 0.4% |

- 로드: 디스크에서 모델을 올리는 시간(처음 한 번). 서버는 적용할 때 미리 올리고(워밍업) 바꿔 끼우므로 면접 중에는 이 시간이 들지 않는다.
- 사후: 녹음 파일 전체를 한 번에 전사(STT 사후 경로). 10~30초 클립에서 small·medium·turbo는 말하는 속도보다 빠르고, large-v3는 약간 느리다(30초 녹음에 약 36초).
- 스트리밍: 마이크처럼 말하는 속도로 PCM을 흘려 넣고(`pcm_chunks(realtime=True)`), 발화가 끝난 시점부터 그 발화의 확정 전사가 나오기까지 걸린 시간. greedy(beam 1).
- 1회차 large-v3 스트리밍은 측정 도중 PC가 절전에 들어가 버렸다(표는 2회차).

### 전사 품질 체감

- **medium 이상은 한국어 낭독을 거의 그대로 받아 적는다.** large-v3는 세 클립 모두 글자 오류 0, turbo는 띄어쓰기 한 곳("아열대폭풍")과 "돌연변이만이 → 돌연변이 많이" 한 곳, medium은 "생식 계열 → 생식기열", "자녀 → 잔여" 두 곳이었다.
- **small은 실사용이 어렵다.** 11.5초 샘플에서 "커리는 약용 식물과 … 기본으로 … 곁들이는"을 "컬이는 야경식물과 … 기보드로 … 겉드리는"으로 적었다(CER 27%). 쉬운 문장은 맞지만 고유명사·전문어가 많은 면접 답변에는 맞지 않는다.
- 스트리밍 CER이 사후보다 조금 높은 것은 발화 단위로 잘라 greedy로 디코딩하기 때문이다(문맥이 짧다). medium은 5.4%로 화면 표시와 꼬리질문 입력에는 쓸 만하다.
- 기술 용어 힌트(initial prompt)는 정확도를 확실히 올리지 않았다. small에 "반도체 공정, CMP, 식각, 수율, SPC"를 넣어도 이 샘플(요리 문장)의 오류는 같았다. 힌트는 실제 면접 녹음과 그 직군 용어로 다시 봐야 한다.

## 왜 실시간이 느린가

Whisper(CTranslate2)는 호출할 때마다 30초 창 전체를 인코딩한다. 그래서 2초짜리 발화도 30초짜리와 인코딩 비용이 같다. 이 노트북에서 인코더 한 번이 medium 약 5초, turbo·large-v3 약 8초였다. 실시간 경로는 이렇게 맞췄다(`providers/stt/faster_whisper.py`).

- 발화가 끝나면(침묵 0.5초) 그 발화를 한 번 디코딩해 확정 전사를 낸다.
- 부분 전사는 호출 비용의 두 배보다 자주 만들지 않는다. 이 CPU에서는 medium부터 사실상 확정 전사만 나온다(small은 부분 전사가 나온다).
- 디코딩이 밀리면 그사이 끝난 발화를 한 번에 디코딩해 30초 창 비용을 나눠 낸다. 지연이 계속 쌓이지 않고 한두 번 호출 시간 안에 머문다.
- 부분 전사를 1.5초마다 만들던 첫 구현은 medium에서 지연이 10초 → 130초로 계속 늘었다(호출 하나가 5초인데 1.5초마다 새 호출). 지금 방식으로 28.9초 클립의 확정 지연이 약 10초에서 멈춘다.
- 측정용 소스는 디코딩하는 동안에도 말하는 속도로 큐에 쌓인다. 실제 마이크·WebRTC 입력(`AudioSource`)도 이렇게 디코딩과 따로 받아 큐에 쌓아야 한다.

## 권장

- **사후 전사(STT 사후)**: large-v3. 30초 녹음에 30~40초, 면접 1시간이면 약 1시간 10분(배치라 문제없음). 메모리 3.3GB. 빨리 받아 봐야 하면 turbo(정확도 거의 같음, 1.1~1.4배).
- **실시간(STT 실시간)**: 화면 권장은 정확도 기준 medium이다. 이 노트북에서는 발화 끝 뒤 확정까지 8~12초 걸려 "실시간 부분 전사 0.5초 이하"(11단계 완료 기준)는 CPU로는 맞출 수 없다. 선택지:
  1. small: 3~8초로 빠르지만 오류가 많다(13%).
  2. GPU가 있는 서버: faster-whisper는 CUDA에서 훨씬 빠르다(여기서는 재지 못함). 같은 provider에 device 옵션을 열고 CUDA 런타임을 깔면 된다.
  3. Google Chirp(사내 GCP, 10·11단계): 진짜 스트리밍 API라 지연이 짧다.
  4. 확정 지연을 감수하고 medium을 쓴다. 꼬리질문은 답변이 끝난 뒤에 요청하므로 확정 지연만큼 늦어진다.
- 메모리: 두 역할을 다 Whisper로 두면(medium + large-v3) 약 5GB를 상시 쓴다. 16GB 노트북에서는 다른 작업과 함께 여유가 크지 않다.

## 다시 재는 법

```bash
uv sync --extra whisper
# 관리자 화면에서 재고 싶은 모델을 내려받은 뒤
uv run python scripts/bench_whisper.py --manifest clips.json --sizes small medium large-v3-turbo large-v3 --json result.json
```

`clips.json`은 `[{"file": "a.wav", "text": "정답 전사"}, ...]`(manifest 기준 상대 경로). 모델마다 별도 프로세스로 돌려 메모리를 따로 잰다. 실제 면접 녹음(동의 받은 것)으로 다시 재야 면접 환경의 정확도를 알 수 있다.
