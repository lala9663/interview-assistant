# BGE-M3 측정 (이 노트북)

> 다루는 것: 로컬 임베딩 BGE-M3를 이 노트북에서 직접 잰 속도·메모리·한국어 검색 적중률, int8 비교(권장), 꼬리질문 지연.
>
> 상태: 구현됨(측정 2026-10-27, int8·지연 2026-10-28) · 확인: 2026-10-30

처음 측정(아래 "조건"~"실측")은 fp32다. 지금 권장은 int8이고 그 비교는 "int8 양자화". 고른 이유는 [model-selection.md](model-selection.md) 6장, 쓰는 곳은 [question-bank.md](question-bank.md).

## 조건

| 항목 | 값 |
| --- | --- |
| PC | Intel i7-1360P (성능 코어 4 + 효율 코어 8, 16스레드), RAM 16GB, GPU 없음, Windows 11, 전원 연결 |
| 다른 작업 | 브라우저·메신저 등이 열려 있어 측정 중 남은 메모리 2.7~3.3GB |
| 모델 | BAAI/bge-m3 커밋 `5617a9f`, 공식 ONNX fp32(데이터 2.27GB) + 희소 헤드, 받은 크기 합계 2.29GB |
| 실행 | ONNX Runtime 1.31 CPU, tokenizers 0.23, 스레드 6(자동), 최대 512토큰 |
| 다시 재기 | `uv run --with psutil python scripts/bench_embedding.py`, `uv run python scripts/eval_retrieval.py` |

## 속도와 메모리

| 항목 | 결과 |
| --- | --- |
| 모델 로딩 | 2.1~2.4초 (디스크 캐시가 데워진 상태. 다운로드 직후 첫 로딩은 더 걸릴 수 있다) |
| 답변 1건 임베딩 (174토큰, 대본 답변 하나) | 중앙값 0.89~0.90초, p90 0.91초 (가장 빠를 때 0.59초) |
| 짧은 질문 1건 (약 20토큰) | 중앙값 0.16초 |
| 질문 은행 1,000건 색인 (짧은 질문, 16개씩) | 156초 (건당 약 0.16초). 데모 질문 은행(질문·꼬리질문 예시 87개)은 약 11초 |
| 검색 (1,000건, 하이브리드, 직군 필터, 상위 24) | 중앙값 9ms, p90 10ms |
| 메모리: BGE-M3만 | 서버 프로세스 1.55GB(로딩 직후) → 1.62GB(1,000건 색인 뒤) |
| 메모리: + Whisper medium (같은 프로세스) | 2.54GB |
| 메모리: + PaddleOCR 작업 프로세스 (한 쪽 읽은 뒤) | 작업 프로세스 0.60GB, 합계 3.15GB. PaddleOCR은 읽는 동안 1.3~1.6GB까지 오른다([ocr-benchmark.md](ocr-benchmark.md)) |
| Whisper medium을 올린 뒤 답변 1건 | 0.93초 (쉬고 있을 때는 서로 늦추지 않는다) |

- **스레드**: 하이브리드 CPU라 많이 쓸수록 느리다(174토큰 기준 중앙값: 4스레드 1.23초, 6스레드 0.87초, 8스레드 0.70~1.15초, 12스레드 1.18초, 16스레드 1.60초). 효율 코어에 걸린 스레드가 매 단계를 늦춘다. 자동 값을 "코어 수의 절반, 최대 6"으로 정했다. 같은 조건에서도 값이 0.6~1.2초로 흔들려(발열·전원 관리) 중앙값으로 적었다.
- **묶어 보내도 빨라지지 않는다**: 짧은 질문 16개를 한 번에 보내도 건당 0.16초로 한 개씩과 같다(CPU 계산량이 그대로). 재색인은 백그라운드에서 돌고 그동안 이전 색인으로 검색하므로, 1,000건에 2~3분은 화면을 막지 않는다.
- **꼬리질문 첫 후보까지**: 질문 은행 후보는 답변 임베딩(약 0.9초) + 검색(10ms 안팎) 뒤에 뜬다. 같은 면접에서 이미 한 질문은 캐시해 두어 새로 임베딩하는 것은 답변과 직전 질문뿐이다. AI 후보는 그 뒤 LLM 첫 글자까지 기다리므로 질문 은행 후보가 먼저 보인다. 브라우저 확인 때 잰 값은 관리자 > 꼬리질문 지표에 남는다(아래 "실측").
- **DLL 충돌 없음**: ONNX Runtime에는 Intel OpenMP(`libiomp5md.dll`)가 없다. Whisper(CTranslate2)와 한 프로세스에서 어느 순서로 올려도 정상(`tests/test_bge_m3.py`), 관리자 API로 PaddleOCR·Whisper·BGE-M3를 함께 켜도 셋 다 동작(`tests/test_engines_together.py`). 그래서 BGE-M3는 별도 작업 프로세스 없이 서버 프로세스에서 돈다.

## 한국어 검색 품질

`tests/fixtures/retrieval_eval.yaml`: 가상의 면접 답변 37개와 그 답변 뒤에 물을 만한 질문 은행 질문(정답 1~2개). 검색 대상은 데모 질문 은행의 승인된 질문과 꼬리질문 예시 87개, 답변의 직군 안에서 찾는다. 정답이 상위 3개 안에 들면 적중. 답변은 전문 용어·약어가 질문과 그대로 겹치는 것(term 8), 같은 뜻을 다른 말로 쓴 것(paraphrase 22), 섞인 것(mixed 7)으로 나눴다.

| | 상위 3개 적중 | 1위 적중 | MRR |
| --- | --- | --- | --- |
| **BGE-M3 하이브리드** (의미 + 0.3 × 단어 일치) | **94.6%** (35/37) | **83.8%** | 0.893 |
| BGE-M3 의미 벡터만 | 94.6% | 78.4% | 0.870 |
| Fake 임베딩 (단어·두 글자 조각 해시) | 75.7% | 45.9% | 0.634 |

| 종류 | 하이브리드 상위 3 / 1위 | 의미만 상위 3 / 1위 |
| --- | --- | --- |
| term (FDC, SPC, DOE, CVD, SLO, GPU …) | 100% / 100% | 100% / 87.5% |
| paraphrase | 90.9% / 72.7% | 90.9% / 68.2% |
| mixed | 100% / 100% | 100% / 100% |

- 희소(단어 일치) 점수는 약어가 그대로 겹치는 답변의 1위를 끌어올린다(87.5% → 100%). 약어는 여러 토큰으로 쪼개진다(FDC = `▁F` + `DC`, CVD = `▁CV` + `D`). 그 토큰들에 가중치가 붙는 것을 테스트로 본다.
- 놓친 2건: "설비 센서 기록을 시간 순서로 늘어놓고…"(정답 FDC 변수·인과 검증, 상위 3개는 가장자리 수율·챔버 구분·판단 실수 수습)와 "인터뷰에서 사람들이 결제 직전에 가장 많이 망설인다는 걸 알고…"(정답 "리서치 결과를 디자인 결정으로", 상위 3개는 사용성 테스트·인터뷰 설계·흐름 단순화). 둘 다 직군 안의 이웃 질문으로 갔다.
- 평가 세트가 작고(37개) 직접 지어낸 것이라 실제 면접 답변에서는 달라질 수 있다. 실제 운영에서는 관리자 > 꼬리질문 지표의 출처별 채택률로 본다.

## 임계값 보정

| 설정 | BGE-M3 기본 | 근거 |
| --- | --- | --- |
| `duplicate_threshold` (같은 질문으로 볼 유사도) | 0.85 | 같은 뜻의 질문 쌍 8개 중 7개가 0.889~0.987(나머지 1개는 주제만 같은 쌍으로 0.59), 다른 질문 쌍 10개는 0.385~0.747(가장 높은 것은 "범위 밖 문제를 주도" vs "판단 실수를 수습"). 그 사이 |
| `min_score` (질문 은행 제안 최소 점수) | 0.55 | 평가 세트에서 정답 질문의 점수 0.466~0.785(중앙값 0.65), 다른 직군에서 가장 높은 것 0.403~0.683(중앙값 0.537). 겹치므로 직군·역량·차수 필터를 먼저 걸고 그 안에서 약한 후보를 덜어내는 값으로 둔다 |
| `sparse_weight` (단어 일치 가중치) | 0.3 | BGE-M3 논문의 밀집 + 희소 결합 예(1 : 0.3). 평가 세트에서 의미만 쓸 때보다 1위 적중이 올랐다 |

Fake 임베딩은 점수 척도가 달라 따로 둔다(0.8, 0.15, 0.3). 이 값들은 관리자 > 모델 설정 > 임베딩의 옵션이고, 바꿔도 벡터를 다시 만들지 않는다.

## 실측 (브라우저 확인, 이 노트북)

데모 DB 사본과 별도 포트의 서버에서 BGE-M3 + fake LLM(speed 1, 첫 글자 0.55초 흉내)으로 잰 값이다.

| 항목 | 결과 |
| --- | --- |
| fake → BGE-M3 적용 뒤 재색인 (질문·예시 87, 평점 기준 15, 역량 사전 3 = 105건, 모델 로딩 포함) | 22.7초. 그동안 이전(fake) 색인으로 검색 |
| 새 답변의 꼬리질문: 첫 질문 은행 카드 / 첫 AI 카드 | 0.6초 / 1.7초 |
| 같은 답변으로 다시 요청 (임베딩 캐시) | 20~45ms / 1.0~1.1초 |
| 서버를 막 띄운 직후 첫 요청 (모델이 아직 올라가는 중) | 4.7초 / 5.7초 |
| 관리자 > 꼬리질문 지표 (요청 15건, 시드의 과거 AI 제안 포함) | 질문 은행 중앙값 306ms·p90 4.0초, AI 중앙값 1.4초·p90 5.1초 |

배치 전체(질문 은행 2개 + AI 3개)는 약 10초 걸린다. fake LLM이 글자를 천천히 흘리고, AI 후보가 완성될 때마다 중복 확인용으로 한 번씩(약 0.2초) 임베딩해서다.

## int8 양자화 (2026-10-28)

꼬리질문의 AI 후보가 답변 임베딩 시간만큼 늦게 출발해서(질문 은행 예시를 프롬프트에 넣으려면 검색이 먼저 끝나야 한다) 같은 모델의 int8 변형을 재고 비교했다. 관리자 > 모델 설정 > 임베딩 > BGE-M3 (로컬)의 모델 선택지 "BGE-M3 (int8 ONNX)"이고, 받기·적용·재색인은 fp32와 같다.

### 출처와 검증

| 항목 | 값 |
| --- | --- |
| 출처 | Hugging Face `Xenova/bge-m3` 커밋 `4de1325`(2026-02-10). Hugging Face transformers.js 팀이 BAAI/bge-m3를 ONNX로 바꾼 저장소. 같은 sentence-transformers 내보내기(출력 `sentence_embedding`, `token_embeddings`)를 동적 양자화한 `onnx/sentence_transformers_int8.onnx` |
| 양자화 | `quantize_config.json`: 가중치 QInt8, 채널별(per_channel), reduce_range(7비트 범위). 활성값은 실행 중 양자화(동적). 단어 임베딩 표(Gather)도 int8 |
| 라이선스 | MIT (모델 카드 `license: mit`, 원본 BAAI/bge-m3와 같음) |
| 파일과 sha256 | `model.onnx` 568,599,071바이트 `e5b42096865cef734247dd8c7a44e35d305b70ba0c3736758065e1cad50f6453` · `tokenizer.json` 17,082,821바이트 `6710678b…f790`(BAAI의 것과 바이트까지 같음) · 희소 헤드 `sparse_linear.pt`는 BAAI/bge-m3 커밋 `5617a9f`에서(`45c93804…5ad9`). 합계 0.59GB, `weights/bge-m3/onnx-int8/` |
| 색인 키 | `BAAI/bge-m3-int8@4de1325/1024`. fp32(`BAAI/bge-m3@5617a9f/1024`)와 벡터가 조금 달라 키를 따로 두고, 바꾸면 다시 색인한다 |
| 희소 헤드 | 같은 코드로 동작한다. 같은 문장의 fp32와 int8 비교: 밀집 벡터 코사인 0.978~0.983, 단어 일치 가중치 상관 0.985~0.993. 약어 토큰(`▁F`+`DC`, `▁CV`+`D`, `▁RF`) 가중치 테스트가 int8에서도 통과(`tests/test_bge_m3.py`, 두 모델 모두) |

공식 int8은 BAAI가 내지 않는다. 직접 양자화(`onnxruntime.quantization`)도 가능하지만 받기 화면이 받을 주소와 해시를 고정해야 해서, 받은 그대로 sha256으로 확인할 수 있는 공개 변환본을 썼다. reduce_range 없이(8비트 그대로) 양자화하면 품질 손실이 더 작을 수 있으나 VNNI가 없는 CPU에서 값이 넘칠 수 있어 시도하지 않았다(남은 과제).

### 속도와 메모리 (같은 조건, 번갈아 두 번)

`bench_embedding.py --model …`를 fp32 → int8 → fp32 → int8 순서로 각각 새 프로세스에서 돌렸다. 호출 30번씩의 중앙값·p90. 측정 중 남은 메모리는 1.1~2.2GB(브라우저 등이 열려 있었다).

| 항목 | fp32 (1회 / 2회) | int8 (1회 / 2회) |
| --- | --- | --- |
| 모델 로딩 (3번 중앙값) | 4.06초 / 3.77초 | 2.24초 / 2.35초 |
| 답변 1건 (174토큰) 중앙값 · p90 | 0.44초·0.47초 / 0.74초·0.80초 | **0.28초·0.29초 / 0.28초·0.29초** |
| 짧은 질문 1건 중앙값 · p90 | 71ms·77ms / 114ms·123ms | 49ms·52ms / 58ms·74ms |
| 질문 1,000건 색인 (16개씩) | 90초 / 129초 | **46초 / 47초** |
| 16개 묶음 하나 중앙값 · p90 | 1.43초·1.79초 / 2.09초·2.37초 | 0.69초·0.94초 / 0.73초·0.88초 |
| 1,000건 검색 (하이브리드, 상위 24) | 7ms / 8ms | 7ms / 8ms |
| 메모리: 로딩 직후 → 1,000건 색인 뒤 | 1.55GB → 1.62GB | **0.92GB → 0.98GB** |
| 메모리: + Whisper medium | 2.45~2.54GB | 1.90GB |
| 메모리: + PaddleOCR 작업 프로세스 합계 | 3.12~3.15GB | 2.51GB |
| Whisper를 올린 뒤 답변 1건 | 0.72~0.79초 | 0.29초 |

- fp32는 같은 조건에서도 0.44초와 0.74초로 크게 흔들렸다(어제는 0.9초). 남은 메모리가 1GB 남짓이라 2.3GB 가중치의 페이지가 밀려났다 돌아오는 것으로 보인다. int8은 두 번 모두 0.28초로 안정적이다. 답변 임베딩은 1.6~2.7배, 색인은 2~2.8배 빠르고 메모리는 0.63GB 적다.
- 검색 시간은 벡터가 같은 float32라 차이가 없다.

### 검색 품질 (같은 평가 세트 37개)

`eval_retrieval.py --model bge-m3-int8`. 하이브리드(의미 + 0.3 × 단어 일치) 기준.

| | 상위 3개 적중 | 1위 적중 | MRR | 상위 4개 (프롬프트 예시 수) |
| --- | --- | --- | --- | --- |
| fp32 | 94.6% (35/37) | 83.8% (31) | 0.893 | 36/37 |
| int8 | 91.9% (34/37) | 81.1% (30) | 0.881 | 35/37 |

| 종류 | fp32 상위 3 / 1위 | int8 상위 3 / 1위 |
| --- | --- | --- |
| term (약어·용어) | 100% / 100% | 100% / 100% |
| paraphrase | 90.9% / 72.7% | 86.4% / 68.2% |
| mixed | 100% / 100% | 100% / 100% |

- 37개 중 5개의 순위가 바뀌었다. 나아진 것 2개(3위 → 1위 "같은 날 처리한 웨이퍼를 장비 위치별로…", 3위 → 2위 "한 기능이 느려지자 연결을 기다리는 요청이…", 그리고 9위 → 7위), 나빠진 것 2개(1위 → 2위 "자주 읽히는 결과를 메모리에…", 1위 → 5위 "제가 밀어붙인 조건 변경 때문에 불량이 늘어서…", 정답은 "판단 실수를 수습한 경험"). 합치면 상위 3개·1위가 한 개씩 줄었다. 약어·용어가 겹치는 답변은 그대로다.
- 37개는 지어낸 작은 세트라 한 개 차이는 흔들림 범위 안이다. 실제 운영에서는 관리자 > 꼬리질문 지표의 출처별 채택률로 다시 본다.

### 임계값은 그대로

`duplicates`(같은 뜻 질문 쌍 8개, 주제만 가까운 다른 질문 쌍 10개)를 `tests/fixtures/retrieval_eval.yaml`에 더해 두 모델의 의미 유사도를 쟀다.

| | fp32 | int8 |
| --- | --- | --- |
| 같은 뜻 8쌍 | 0.787~0.961 (중앙값 0.906), 0.85 이상 6쌍 | 0.780~0.954 (중앙값 0.899), 0.85 이상 6쌍 |
| 다른 질문 10쌍 | 0.430~0.750 (중앙값 0.646), 0.85 이상 0쌍 | 0.414~0.767 (중앙값 0.646), 0.85 이상 0쌍 |
| 정답 질문 점수 (37개) | 0.466~0.785 (중앙값 0.650), 0.55 미만 5개 | 0.488~0.795 (중앙값 0.649), 0.55 미만 4개 |
| 다른 직군에서 가장 높은 점수 | 0.419~0.683 (중앙값 0.565) | 0.411~0.675 (중앙값 0.561) |

- `duplicate_threshold` 0.85: 두 모델에서 같은 결과(같은 뜻 6/8을 거르고, 다른 질문은 하나도 거르지 않음). 거르지 못한 두 쌍("재발을 막기 위해…" 0.78~0.79, "장애 직후 제일 먼저…" 0.80)은 0.80으로 내리면 잡히지만 다른 질문 쌍의 최댓값 0.75~0.77과 너무 가까워 그대로 둔다.
- `min_score` 0.55: 분포가 거의 같아 그대로 둔다. 그래서 int8도 BGE-M3 옵션의 기본값을 같이 쓴다.

### 권장: int8

관리자 화면의 권장 모델을 int8로 바꿨다. 품질 손실은 평가 세트 37개 중 한 개(상위 3개·1위 각 2.7%p, MRR 0.012)이고 약어 질의는 그대로이며 임계값도 그대로 맞는다. 대신 답변 임베딩이 0.28초로 안정되고(fp32 0.44~0.74초), 재색인이 절반, 메모리가 0.63GB 적다. 이 노트북처럼 GPU 없이 Whisper·OCR과 한 서버에 올리는 경우에 맞다. 사내 서버에 GPU가 있거나 메모리가 넉넉하고 속도가 충분하면 fp32를 그대로 써도 된다. 모델 반입 크기도 2.29GB → 0.59GB로 준다.

권장값을 바꿔도 이미 쓰는 설정은 바뀌지 않는다(dev.db는 fp32 그대로). 바꾸려면 관리자 > 모델 설정 > 임베딩 > 변경 > BGE-M3 (로컬) > 모델 "BGE-M3 (int8 ONNX)" > 다운로드(0.59GB) > 테스트 > 적용. 적용하면 백그라운드에서 다시 색인하고(데모 105건 14.8초, 모델 로딩 포함. fp32는 22.7초) 그동안은 fp32 색인으로 검색한다. 되돌릴 때도 같다. 진행 중인 면접은 시작할 때의 AI 설정을 고정하므로, 그 면접이 끝나거나 서버를 다시 띄울 때까지 fp32 모델이 메모리에 남을 수 있다(검색은 바로 int8 색인으로 한다).

## 꼬리질문 지연 줄이기 (2026-10-28)

질문 은행 예시를 AI 프롬프트에 넣는 것은 그대로 두고(예시를 넣으려면 검색이 먼저 끝나야 한다), 그 앞뒤의 기다림을 줄였다.

| 바꾼 것 | 전 | 후 |
| --- | --- | --- |
| AI 후보의 중복 확인 | 후보가 완성될 때마다 그 질문을 임베딩(fp32 약 0.1~0.2초)한 뒤에야 `suggestion.done`을 보내고 다음 후보를 읽었다 | 먼저 보여 주고(`checking`) 뒤에서 확인한다. 같으면 카드를 흐리게 했다가 접는다. 확인 중에는 쓸 수 없고, 거둔 후보는 질문으로 기록되지 않는다(API 409) |
| 방금 한 질문의 임베딩 | 답변과 같은 묶음으로 임베딩돼 20토큰 질문이 174토큰 답변 길이로 채워졌다(답변 두 개 값) | 질문을 기록할 때 미리 임베딩(녹음 없는 수기 면접도. 녹음 면접은 듣기 시작할 때 이미 했다) |
| 길이가 크게 다른 텍스트 묶기 | 한 묶음에 넣어 가장 긴 것에 맞춰 채웠다 | 2배 + 16토큰을 넘으면 묶음을 나눈다(CPU에서는 묶어도 빨라지지 않는다) |
| 답변 중 미리 임베딩과 겹칠 때 | 같은 답변을 한 번 더 임베딩(진행 중인 것 뒤에 줄 섬) | 진행 중인 같은 텍스트를 기다려 결과를 같이 쓴다 |

### 브라우저 실측 (fake LLM speed 1)

데모 DB 사본과 별도 포트 서버에서, 브라우저 페이지가 녹음 없는 면접에 새 질문을 기록하고 2초 뒤(지원자가 말하는 시간) 매번 다른 답변(174토큰 남짓)을 입력한 직후 꼬리질문을 요청해, 응답 스트림의 이벤트 시각을 `performance.now()`로 쟀다. 설정마다 준비 1번 + 16번. "전"은 이 작업 직전 커밋(`9aee8f3`)의 코드다.

| (초, 중앙값 / p90 / 최솟값) | 전 · fp32 | 후 · fp32 | 후 · int8 |
| --- | --- | --- | --- |
| 첫 질문 은행 카드 | 1.24 / 3.68 / 1.07 | 1.20 / 2.30 / 0.51 | **0.27 / 0.69 / 0.18** |
| 첫 AI 카드가 뜸 | 2.25 / 4.67 / 2.09 | 2.21 / 3.31 / 1.50 | **1.32 / 1.70 / 1.23** |
| 첫 AI 카드 완성 | 5.25 / 7.86 / 4.94 | 4.99 / 6.11 / 4.12 | 4.25 / 4.68 / 3.98 |
| 배치 완료 (질문 은행 2 + AI 3) | 11.07 / 13.43 / 10.50 | 10.78 / 11.87 / 9.59 | 9.93 / 10.83 / 9.47 |

- **코드 변경만의 효과(fp32 최솟값)**: 첫 질문 은행 카드 1.07 → 0.51초(답변만 임베딩), 첫 AI 카드 2.09 → 1.50초, 배치 완료 10.50 → 9.59초(중복 확인 세 번이 표시를 막지 않음).
- **fp32는 이 노트북에서 흔들린다**: 서버 프로세스의 확정 메모리가 4.4GB인데 실제로 올라와 있는 것은 1.9GB였다(남은 메모리 1~2.6GB). 가중치가 밀려났다 돌아오는 요청이 생겨 전은 16번 중 5번이 3.0~3.7초, 후는 16번 중 11번이 1.1~2.4초로 늘었고, 그래서 중앙값은 전후가 비슷하다. int8은 16번 중 13번이 0.4초 안이었다.
- **AI 카드는 질문 은행 카드보다 약 1.0초 뒤**다. fake LLM의 첫 글자 0.55초 흉내에 역량 태그를 천천히 흘리는 시간이 더해진 것이고 임베딩과는 상관없다. 실제 LLM에서는 그 모델의 첫 토큰 시간이 이 자리에 온다.
- 마이크 면접에서는 답변 중 미리 임베딩(`live/prefetch.py`)으로 답변 임베딩이 대부분 미리 끝나 있어 위 "질문 은행 카드" 시간이 더 짧다. 위 표는 미리 임베딩이 없는 수기 입력(가장 늦은 경우)이다.
- 같은 질문이면 실제로 접히는지는 화면에서 확인했다(fake 후보를 다음 질문으로 쓰고 같은 답을 다시 넣으면 첫 AI 후보가 방금 한 질문과 같아 흐려졌다가 "이미 한 질문과 비슷함" 한 줄로 접히고, 나머지 후보 번호는 이어서 붙는다).

### 마이크 경로: 말 끝 → 답변 닫힘 → 첫 카드

`scripts/bench_live_audio.py --sizes small --turns silence --embedding <bge-m3 | bge-m3-int8> --llm-speed 1 --repeat 2`. 앱의 실제 조각(Silero VAD, 침묵 2초 답변 끝 판정, Whisper small 실시간, 허브, 답변 중 미리 임베딩, 꼬리질문 스트림)을 한 프로세스에서, 표본 WAV 두 개(answer-pauses 16.1초, FLEURS 8.5초)를 실제 시간으로 넣어 쟀다. 시간은 표본의 마지막 말소리(VAD)부터. "전"은 `9aee8f3` 코드(같은 스크립트를 그 코드로 실행). 두 표본 모두 공정개발 질문 은행과 가까운 질문이 없어 첫 카드가 AI 카드다. 같은 노트북에서 다른 세션의 서버가 메모리를 2.7GB 쓰고 있었다(전 · fp32는 그 전 4번과 그 뒤 4번).

| (초, 중앙값, 범위) | 전 · fp32 (8번) | 후 · fp32 (4번) | 후 · int8 (4번) |
| --- | --- | --- | --- |
| 답변 닫힘 → 첫 카드 | 1.43 (1.23~1.59) | 1.29 (1.17~1.45) | **1.10 (1.08~1.14)** |
| 말 끝 → 답변 닫힘 | 4.02 (3.18~7.14) | 4.69 (3.52~10.42) | 6.36 (3.04~7.84) |
| 말 끝 → 첫 카드 | 5.47 (4.41~8.73) | 5.97 (4.71~11.87) | 7.48 (4.11~8.93) |

- **이 작업이 바꾸는 것은 "답변 닫힘 → 첫 카드"다.** 그중 약 1.0초는 fake LLM의 첫 글자 흉내이고, 나머지가 임베딩·검색이다: 전 약 0.43초 → fp32 0.29초 → int8 0.10초. 마이크 경로에서는 답변 중 미리 임베딩이 있지만, 마지막 확정 전사가 오는 순간 답이 닫히므로 마지막 텍스트의 임베딩은 그때 막 시작한다. 전에는 꼬리질문이 그 뒤에 같은 텍스트를 한 번 더 임베딩했고(두 배), 이제는 진행 중인 것을 기다려 같이 쓴다.
- **"말 끝 → 답변 닫힘"은 Whisper가 정한다**(마지막 발화 확정. [audio-input.md](audio-input.md) 9장). 같은 표본이 3.9초 또는 7~8초로 갈리고(디코딩 창 타이밍) 표본 수가 적어 설정 사이의 차이는 이 흔들림 안이다. 이 작업은 이 구간의 코드를 바꾸지 않았다. 그래서 "말 끝 → 첫 카드"의 중앙값도 Whisper 흔들림을 그대로 따른다.
- 다른 세션의 테스트(OCR 작업 프로세스 포함)가 함께 돌던 첫 측정에서는 말 끝 → 답변 닫힘이 35초까지 늘었다. CPU를 나눠 쓰면 Whisper가 가장 먼저 느려진다. 그 측정은 버렸다.

## 남은 측정

- 실제 LLM을 붙인 뒤: 질문 은행 예시를 넣은 꼬리질문의 품질, 첫 AI 후보까지 시간, 출처별 채택률.
- 실제 면접 답변으로 fp32와 int8의 검색 차이(지금은 지어낸 37개).
- reduce_range 없이 직접 양자화한 int8(품질이 더 가까운지, VNNI 없는 CPU에서 괜찮은지).
- GPU 서버(같은 ONNX를 CUDA 실행기로)에서의 속도.
