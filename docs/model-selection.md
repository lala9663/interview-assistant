# AI 모델 선택 메모

2026-10-26 · 관리자 > 모델 설정과 로컬 Whisper를 붙인 뒤 정리한 판단 근거(2026-10-28 GCP 전제 철회 반영). 측정은 [Whisper 측정](whisper-benchmark.md), 교체 구조는 [API 계약](api-contract.md) "관리자 > 모델 설정".

모델은 아직 정하지 않았다. 사내에 어떤 모델(LLM·STT)이 허용되는지 모르고, 실행 위치(사내 서버, 사내 클라우드, 에이전트 플랫폼 안)도 미정이다. 2026-10-21에 PoC를 GCP에서 하기로 정했으나 2026-10-28 철회했다(7장). 그래서 로컬 모델을 먼저 쓰고, 무엇이 정해져도 관리자 화면에서 바꿔 끼우는 구조로 두었다. 사내 에이전트 플랫폼에는 MCP로 붙인다([agent-integration.md](agent-integration.md)). 이 문서는 고를 때의 기준과 지금까지 확인한 사실을 모은다.

## 1. 역할마다 무엇이 중요한가

| 역할 | 언제 | 우선순위 | 비고 |
| --- | --- | --- | --- |
| STT 실시간 | 면접 중, 지원자가 말하는 동안 | 속도 | 면접관 화면에 전사를 바로 띄우고, 답변이 끝나면 꼬리질문을 요청한다. 몇 초 단위로 끊어 받아 적어 오류가 더 난다 |
| STT 사후 | 면접이 끝난 뒤, 녹음 파일 전체로 | 정확도 | 공식 기록과 AI 채점 근거. 앞뒤 문맥이 있어 더 정확하다(같은 Whisper medium이 실시간 5.4%, 사후 1.2% 오류). 대면 면접의 화자분리, 질문-답변 나누기(10단계), 실시간 STT가 끊긴 면접의 기록 복구도 여기서 한다. 느려도 되니 가장 정확한 모델을 쓴다 |
| LLM 꼬리질문 | 면접 중, 답변마다 | 속도 (첫 글자 2초 이하, 7단계) | 지금은 LLM 주 모델을 쓴다 |
| LLM 채점·역량 사전 | 면접 뒤 백그라운드, 답변마다 3회 | 품질 | 면접관 점수와의 일치도가 게이트 기준(12단계) |
| LLM 서류 선별 | 업로드할 때 | 비용 (대량) | |
| 임베딩 | 답변이 끝날 때(꼬리질문 검색), 질문 은행·기준 예시를 승인할 때 | 한국어 검색 품질, 전문 용어, 데이터 위치 | 6장. BGE-M3로 정함(2026-10-27) |

지금 상태: STT 사후는 화면에서 고르고 테스트하는 것까지다. 녹음 파일 저장(11단계)과 사후 전사 흐름(10단계)이 아직 없다. STT 실시간은 마이크 입력을 붙이기 전까지 가상 지원자 대본(fake)이다.

## 2. 답변이 끝나고 꼬리질문이 뜨기까지 (예상)

```
지원자 말 멈춤 ─①─ "답변이 끝났다" 판단 ─②─ 마지막 문장 전사 확정 ─③─ LLM 첫 꼬리질문 글자 ─④─ 후보 2~3개 완성
```

| 구간 | 이 PC (Whisper medium, CPU) | GPU Whisper 또는 스트리밍 STT (외부 클라우드 Chirp·CLOVA, 승인 시) |
| --- | --- | --- |
| ① 답변 끝 판단 | 약 2초 (문장 사이 쉼과 구분하려면 몇 초 기다려야 함) | 약 2초 |
| ② 마지막 문장 확정 | 7.7~8.9초 (측정) | 1초 이하 (추정) |
| ③ LLM 첫 글자 | 1~2초 (추정, 목표 2초 이하) | 1~2초 (추정) |
| 첫 꼬리질문이 보일 때까지 | 약 9~11초 (①은 ②와 겹침) | 약 3~4초 |
| ④ 후보 2~3개 완성 | +3~5초 | +3~5초 |

- Whisper 숫자만 잰 값이다. LLM과 스트리밍 STT는 연결 전이라 추정이다. small을 쓰면 ②가 3.5~5.7초(전체 5~8초)지만 전사 오류가 많아(13%) 꼬리질문 품질도 떨어진다.
- 앞 문장들은 지원자가 말하는 동안 확정되므로 기다리는 것은 마지막 문장 하나다. 답변이 길어도 간격은 같다.
- ①의 침묵 길이는 마이크 입력을 붙일 때 정한다. 짧으면 말하는 도중에 답변이 닫히고, 길면 간격이 는다. 지금 데모는 대본이 끝나면 바로 닫힌다.
- 면접관이 사전 질문이나 직접 쓴 질문을 하면 AI를 기다리지 않는다. 꼬리질문 후보는 옆에 따로 뜬다.
- 더 줄이려면: 1~2초 침묵에서 꼬리질문 생성을 미리 시작하는 방식(답변이 이어지면 버림). 실제 모델로 재고 길면 검토한다.

## 3. 실시간 STT 선택지

자세한 비교는 [reference/stt.md](reference/stt.md).

| 선택지 | 응답 방식 | 속도 | 데이터 위치 | 확인한 것 |
| --- | --- | --- | --- | --- |
| Whisper, 이 PC CPU | 발화가 끝나면 그 구간을 통째로 전사 | 말 끝 → 확정 small 3.5~5.7초, medium 7.7~8.9초 (측정) | 이 PC | 호출마다 30초 창을 통째로 인코딩해 짧은 발화도 비용이 같다. 11단계 기준(부분 전사 0.5초 이하)은 CPU로 못 맞춘다 |
| Whisper, GPU 서버 | 같음 | 훨씬 빠름 (미측정) | 회사 서버 | 같은 provider에 device 옵션을 열면 된다. 음성이 회사 밖으로 안 나가 보안상 가장 좋다 |
| Google Speech-to-Text v2 (Chirp 3) | 스트리밍 API: 말하는 도중 중간 결과, 끝나면 확정 | 공식 수치 없음, 미측정 | 외부 클라우드 (Google), 회사 밖 | `StreamingRecognize` 지원, 한국어 GA. 중간 결과에 `is_final`과 stability. 발화 끝 판단 민감도 조정 가능. 화자분리는 GA지만 비스트리밍 요청(파일 전사)에서만 되고 스트리밍에서는 안 된다([reference/diarization.md](reference/diarization.md) 4장, 2026-10-26에는 Preview로 적었다). 자동 문장부호는 Preview, 단어 시각 미지원. 리전은 us·eu GA, 아시아는 문서마다 표기가 달라 확인 필요 |
| NAVER CLOVA Speech | 스트리밍 API (gRPC) | 공식 수치 없음, 미측정. 네이버 뉴스·쇼핑라이브 실시간 자막에 쓰인다고 발표 | 네이버 클라우드 (한국 리전), 회사 밖 | 한국어·영어·일본어. 입력이 16kHz 모노 16비트 PCM이라 우리 형식과 같다. 발화 끝 신호(`epFlag`)를 보내지 않으면 최대 10초(`unvoiceTime`) 모았다가 확정을 준다. 스트리밍 화자분리가 안 나오는 사례, 채널 15개 한도 |
| Azure, AWS Transcribe, Deepgram 등 | 스트리밍 API | 미측정 | 회사 밖 | 한국어 지원. 음성 원본이 외부로 나간다 |

회사 밖 서비스는 "음성 원본은 외부로 보내지 않음" 원칙에 걸린다. 관리자 화면에서 "외부" 배지와 경고·사유 단계를 거치고, 그 전에 보안 승인이 필요하다.

## 4. 면접 방식별 오디오와 화자 구분

자세한 비교는 [reference/diarization.md](reference/diarization.md), 마이크·에코·답변 끝 판단은 [reference/audio-quality.md](reference/audio-quality.md).

마이크 하나로 여러 사람을 녹음하면 누가 말했는지 가려야 한다(화자분리). 다만 화자분리는 `화자1`, `화자2`처럼 이름 없이 나눌 뿐이고, 그 화자가 누구인지 잇는 단계가 따로 필요하다. 사람이 많을수록, 목소리가 비슷할수록, 말이 겹칠수록 틀리고, 실시간은 사후보다 부정확하다(Chirp 3 화자분리는 GA지만 스트리밍에서는 안 되고, CLOVA도 스트리밍 화자분리가 안 된다). 그래서 **사람마다 소리가 따로 들어오게 해서 화자분리가 필요 없게** 하는 것을 먼저 권한다.

| 상황 | 권장 | 화자분리 |
| --- | --- | --- |
| 비대면 (WebRTC, 11단계) | 참가자마다 오디오 트랙이 따로 들어온다. 트랙 = 사람이라 누가 말했는지 바로 안다 | 필요 없음 |
| 대면, 지원자 1명 | 지원자 자리에 마이크를 따로 둔다. 면접관 쪽은 누가 질문했는지 몰라도 된다(질문은 면접관이 앱에서 기록) | 필요 없음 |
| 대면, 그룹 면접 | 사람마다 마이크(핀·테이블 마이크 + 다채널 오디오 장비) | 필요 없음 (가장 정확) |
| 대면, 방 마이크 하나뿐 | 화자분리 + 면접관이 앱에서 "화자2 = 지원자 B"를 지정하고 고치는 화면 | 필수. 실시간은 부정확, 사후로 보정 |

- 목소리를 미리 등록해 사람을 알아보는 방식(음성 등록)은 생체정보라 개인정보보호법상 민감정보다. 별도 동의가 필요해 권하지 않는다.
- 지금 구조는 **면접관 여러 명 + 지원자 1명**까지 지원한다(패널, 면접관별 점수). 전사의 화자는 "면접관 / 지원자" 두 가지다.

### 그룹 면접(지원자 여러 명)을 하려면

범위 미정. 원래 요구사항("대면/비대면 모두 지원")에 그룹 면접은 없다. 한다면 바뀌는 것:

- 면접 하나에 지원자 여러 명을 묶고, 질문 하나에 여러 지원자의 답변이 달리게 한다.
- 전사 구간의 화자를 "특정 사람"으로 기록하고, 화자분리 결과와 사람이 고친 내역을 남긴다.
- 비식별화: 지원자 A의 답변에 B의 이름이 나올 수 있어 같은 면접 안 모든 지원자의 정보를 함께 가리고, 토큰도 `[지원자-A]`, `[지원자-B]`처럼 구분한다. 녹음 동의는 지원자 전원에게 받는다.
- AI 채점과 꼬리질문은 지원자별로 그 사람의 답변만으로 한다. 화자를 잘못 붙이면 다른 사람의 답변으로 채점되므로, 화자 지정이 확실한 구간만 채점한다.

권장: PoC는 지원자 1명 + 면접관 여러 명으로 두고, 대면은 지원자 마이크를 따로 둔다. 그룹 면접은 Phase 2 과제.

## 5. 조합

### 회사에 확인할 것

1. 실행 위치: 사내 서버, 사내 클라우드, 에이전트 플랫폼 안 중 어디인가
2. GPU 서버를 받을 수 있는가
3. 사내 LLM을 제공하는가(에이전트 플랫폼이 주는 것 포함), API 형식은 무엇인가. OpenAI 형식 API면 `open_model_server`로 붙는다(OpenAI 서비스는 쓰지 않는다). 없으면 사내 서버에 오픈 웨이트 모델을 설치할 수 있는가([reference/llm.md](reference/llm.md))
4. 사내 STT가 있는가, 면접 음성을 회사 밖으로 보내도 되는가
5. 외부 클라우드 API(Google·Azure·AWS 등)를 쓸 수 있는가, 쓴다면 데이터를 어느 리전에 둬야 하는가
6. 어떤 에이전트 플랫폼이 들어오는가([agent-integration.md](agent-integration.md) 8장)

### 답에 따른 조합

| 상황 | STT 실시간 | STT 사후 | LLM |
| --- | --- | --- | --- |
| GPU 서버가 있다 | 로컬 Whisper (GPU) | 로컬 Whisper large-v3 | 사내 LLM 또는 GPU에 설치한 오픈 웨이트 모델 |
| 승인된 외부 클라우드만 있다 | 그 클라우드의 스트리밍 STT | 그 클라우드의 배치 STT 또는 로컬 Whisper large-v3 | 그 클라우드의 LLM |
| 둘 다 없다 | 로컬 Whisper CPU (확정까지 8초 이상 감수, 또는 small) | 로컬 Whisper large-v3 | 사내 LLM |

### PoC (실행 위치가 정해질 때까지: 로컬 우선)

"이 서비스가 면접에서 쓸 만한가"를 빨리 보이기 위한 임시 선택이다. 2026-10-21에는 직접 만들 GCP 프로젝트(STT 실시간 Chirp 3 스트리밍, LLM Vertex AI의 Claude)로 정했으나 2026-10-28 철회했다.

- STT 실시간: 로컬 Whisper. GPU가 없으면 small(이 노트북 마이크 측정에서 말 끝부터 답이 닫히기까지 평균 5~7초, medium은 17~20초라 못 따라간다), GPU가 있으면 medium 이상 ([audio-input.md](audio-input.md) 8~10장). 외부 클라우드 스트리밍 STT(Chirp 3 등)는 승인 시 대안
- STT 사후: 로컬 Whisper large-v3 + 면접 뒤 녹음 재전사 (샘플 오류 0%, 녹음 길이의 약 1.2배)
- LLM: 사내 LLM(플랫폼 제공) 또는 사내에 설치한 오픈 웨이트 모델에 OpenAI 형식 API provider(`open_model_server`)로 붙는다(OpenAI 서비스는 쓰지 않음, 모델 서버 위치 미정). 모델 비교는 [reference/llm.md](reference/llm.md), 꼬리질문은 주 모델로 재 보고 결정
- 화자: 한 마이크 대면 면접은 질문 중 / 답변 듣는 중 전환(Alt+1/Alt+2)으로 면접관·지원자를 나누고, 재전사에도 그 역할 기록을 붙인다([audio-input.md](audio-input.md) 4·8장). 화자분리 모델(방 마이크 하나·그룹 면접)은 남은 과제로, 로컬 후보는 pyannote community-1, Chirp 3(외부 클라우드)은 GA지만 비스트리밍 요청에서만 ([reference/diarization.md](reference/diarization.md))
- 연결: 사내 에이전트 플랫폼에 MCP로 ([agent-integration.md](agent-integration.md))

`config/providers.yaml`의 STT 기본값은 2026-10-28부터 로컬 Whisper(실시간 small·빔 1, 사후 large-v3·빔 5 + 면접 뒤 녹음 재전사)다. 화자분리 기본값은 2026-10-21 결정 때의 `google_stt_v2`(구현 전)로 아직 남아 있다.

판단 기준: 실시간 부분 전사 0.5초 이하, 꼬리질문 첫 글자 2초 이하, 실제 면접 녹음의 오류율. 실행 위치와 모델이 정해지면 관리자 화면의 연결 테스트와 `scripts/bench_whisper.py`처럼 같은 조건에서 잰다.

## 6. 임베딩: BGE-M3 (2026-10-27 결정)

사용자가 BGE-M3(BAAI/bge-m3, MIT, 1024차원, 최대 8,192토큰)로 정했다. 측정은 [embedding-benchmark.md](embedding-benchmark.md), 쓰는 곳은 [question-bank.md](question-bank.md).

**어디에 쓰나: 질문 쪽에만.**

- 직군·역량별로 채용 담당자가 검수한 질문 은행을 임베딩해, 답변이 끝나면 가까운 승인 질문을 즉시 제안한다(LLM 후보는 이어서 스트리밍). 첫 후보까지의 간격(2장)을 LLM을 기다리지 않고 줄이는 방법이다.
- 검색한 좋은 질문을 LLM 프롬프트의 예시(few-shot)로 넣는다.
- 이미 한 질문·이전 차수에서 한 질문과 뜻이 같은 후보를 걸러낸다.
- 비슷한 직군의 확정 역량 사전을 찾아 역량 사전 초안의 예시로 쓴다.
- 평점은 사람이 검수한 가상 기준 예시 답변(역량별 1~5점)을 기준점으로만 준다. 임베딩은 기준 예시끼리 겹치지 않는지 보는 데만 쓴다.

**하지 않는 것.** 모범 답안과의 유사도로 점수 매기기(외운 답변이 유리해지고 공정성을 해친다), 지난 지원자의 실제 답변 임베딩(목적 외 이용, 편향 전파). 둘 다 테스트와 DB 제약으로 막았다. 질문 은행은 금지 질문(가족, 출신지, 결혼 여부 등)을 줄이는 법적 안전장치이기도 해서, 승인 전에 규칙과 AI로 금지 질문을 경고한다.

**어떻게 돌리나: 공식 ONNX + ONNX Runtime.**

| | FlagEmbedding (공식 파이썬 라이브러리) | 공식 ONNX + ONNX Runtime (선택) |
| --- | --- | --- |
| 추가 설치 | torch + transformers (1GB 이상) | 없음. onnxruntime·tokenizers는 faster-whisper가 이미 쓴다 |
| 희소(단어 일치) | 지원 | ONNX가 마지막 은닉층을 내므로 희소 헤드(가중치 1024개 + 편향)를 곱해 같은 값을 만든다. 헤드 파일은 pickle을 실행하지 않고 바이트로 읽는다 |
| DLL 충돌 | torch가 Intel OpenMP(`libiomp5md.dll`)를 실어 PaddleOCR 때와 같은 충돌 위험 | ONNX Runtime에는 없음. Whisper와 한 프로세스에서 어느 순서로도 정상(테스트) |
| 라이선스 | MIT (FlagEmbedding), BSD (torch), Apache-2.0 (transformers) | MIT (ONNX Runtime), Apache-2.0 (tokenizers), MIT (모델) |

멀티벡터(ColBERT) 출력은 쓰지 않는다. 질문이 짧아 밀집 + 희소로 충분했다(평가 세트 상위 3개 적중 94.6%).

**결과 요약 (이 노트북):** 로딩 2.1~2.4초, 서버 메모리 +1.6GB, 답변 1건 임베딩 약 0.9초, 짧은 질문 0.16초, 질문 1,000건 재색인 약 2.6분(백그라운드, 그동안 이전 색인으로 검색), 1,000건 검색 9ms. 한국어 평가 세트 37개: 상위 3개 적중 94.6%, 1위 적중 83.8%(의미만 78.4%, 약어 질의는 100% vs 87.5%).

**대안:** Vertex AI 임베딩(gemini-embedding-001 등)은 카탈로그에만 두었다(외부 클라우드 Google, 구현 전, 승인 시 대안). 관리자 화면에서 바꾸면 백그라운드로 재색인하고 그동안 이전 색인으로 검색한다.

## 7. 정한 것과 미룬 것

| 항목 | 결정 | 언제 다시 |
| --- | --- | --- |
| 실행 위치 | 미정 (사내 서버 / 사내 클라우드 / 에이전트 플랫폼 안). 로컬에서 먼저 돌리고 사내 에이전트 플랫폼에 MCP로 붙인다. 2026-10-21 "PoC는 GCP"로 정했으나 2026-10-28 사용자가 철회했다 | 회사 확인 1번(5장)의 답이 오면 |
| 꼬리질문 전용 LLM 역할 | 지금은 만들지 않는다. 주 모델로 2초를 맞추는지 모르고, 사내 허용 LLM이 하나뿐일 수 있다. 필요하면 관리자 화면에 역할 하나를 더하는 작은 작업이다 | 3단계에서 꼬리질문 첫 글자 시간과 비용을 잰 뒤 |
| 데이터 위치 배지 "사내 GCP" | 정함 (2026-10-28). Google·Vertex 계열은 "외부 클라우드 (Google)"로 바꾸고 회사 밖 전송 확인을 받는다. 사내 모델 서버용 "설정한 사내 서버"를 더했다. 2026-10-26에는 "사내 GCP"로 표시하고 외부 경고를 띄우지 않았다 | 외부 클라우드를 승인받으면 |
| 답변 끝 판단 침묵 길이 | 미정 (2초 안팎 예상) | 실시간 면접 마이크 입력을 붙일 때 |
| 실시간 STT | 미정. 이 PC CPU의 Whisper로는 11단계 기준을 못 맞춘다 | 회사 확인 항목(5장)의 답이 오면 |
| 그룹 면접·화자 지정 | 범위 미정. PoC는 지원자 1명 + 면접관 여러 명, 대면은 지원자 마이크 따로 (4장) | 업무정의서 범위를 정할 때 |
| 임베딩 모델 | BGE-M3, 로컬 CPU, ONNX Runtime (6장) | 실제 면접 답변으로 채택률을 본 뒤, 메모리가 빠듯하면 int8 양자화나 GPU |
| 벡터 검색 엔진 | 메모리 내 전수 검색(수천 건), 저장은 엔진 독립(BLOB·JSON) | DB 엔진(PostgreSQL/MySQL)을 정할 때 pgvector 등 |
